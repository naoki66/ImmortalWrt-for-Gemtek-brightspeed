# WM/WA 其他路径核对与故障原因复核

本轮继续做离线代码/机器指令核对，没有连接或修改实机，没有切网、重启无线、开启 RED，也没有编译新的可刷固件。

**结论：收窄了排查范围，但还未定位到一条能经实机复现并证明根因的 WM/WA 指令或源码错误。** 当前最强证据仍指向 2.4GHz 高上行负载时 TCP ACK 返回路径的排队/竞争；原先三频 Wi-Fi 消失则有 MCU 无响应、PCIe 完成超时与恢复失败证据。二者不能直接合成一个原因。

## 一、优先级与 AC 队列映射：完整函数核对通过

原厂 WA `map_acm_up_to_ac` 入口 `0x1000aa84`，当前 WA `0x10009fc0`。本轮对这两个完整解码函数逐指令解释执行，使用各自固件中的真实映射表：

- UP→AC：`{1,0,0,1,2,2,3,3}`，即 UP0/3→BE，1/2→BK，4/5→VI，6/7→VO。
- AC→代表 UP：`{1,0,5,7}`。
- 相关准入判断标志位未置位时直接保留初始映射；置位时按对应 ACM 位检查，并向更低优先级降级，最低到 BK。
- 输入中的低 2 个标志位保留；非法 UP 的路径有单独边界判断，不把它当作合法 UP 索引越界访问。

遍历全部 256 个输入字节、16 种 ACM 掩码、两种判断标志状态、两个固件，共 **16,384 组**、400,256 条解释执行指令。返回 AC 与修改后的优先级字节均与独立模型一致，原厂/当前结果一致。测试关闭调试输出，未调用任何外部日志函数。结果文件 `ac-mapping-review-tests.json`。

这验证了这个映射函数及表，不代表整条数据面等价。当前没有证据把 2.4GHz 问题归因于这里的 BE/BK 映射差异。

## 二、BA 字段解析：未见 256 被截为零的证据

当前主机 `mt7996_mcu_sta_ba()` 使用 `cpu_to_le16(params->buf_size)` 填入 `winsize`。WA 两版的 BA 调试路径都用 `lhu` 从 TLV `+0x0a` 读取窗口：原厂 `0x1000c248`，当前 `0x1000b458`。该读取与 16 位小端布局相符，窗口 256 不会因这个读取动作截断成 8 位零。

这只是字段布局和读取核对，尚未证明两版整个 BA 状态机、WTBL 写入、RRO 行为完全一致。过去对照已实际把 RX BA 从 256 调到 64/16，未改善下行饥饿；不能仅凭字段相符或 BA 建立就认定聚合行为一定正常。

相关源码：当前 `mt7996/mcu.c:1887` 的 `mt7996_mcu_sta_ba()`；`mt76_connac_mcu.h` 与 `mt7996/mcu.h` 的 BA 结构。当前实际发送的是 `sta_rec_ba_uni`，未误用其他芯片的普通 BA 结构作 ABI 结论。

## 三、RED/ACM 与 ACK 迟到的因果关系

上轮已核对 ACM 配置及阈值换算，本轮进一步核对当前主机初始化：`mt7996_mcu_init_firmware()` 最后明确发送 `MCU_WA_PARAM_RED, 0, 0`。这说明当前代码的初始化意图是关闭 WA RED；本轮没有实机读回，不能据此声称芯片所有 RED/准入模块的运行态一定为零。

原厂主机 RED 配置与当前初始化确有差异，但不能直接推出“打开原厂 RED 就能修复”：

1. 已定位的 WA RED/ACM 配置、逐 STA TX 状态和主机投递队列主要涉及 AP 数据发送侧。它们不是终端发送队列的直接控制接口。
2. 已有真实 ACK 分段记录显示，主要等待在电脑提交 ACK 之后、AP 硬件接收之前。修改 AP 下行丢弃或量子，可以间接改变空口竞争，但不能据此宣称消除了这段等待。
3. 前期少量上传早期丢包对照，把约 176/4.55 Mbps 调整为约 90/93 Mbps，说明拥塞反馈和上下行竞争能显著改变分配；这是机制证据，不是独立的驱动根因，也不是总容量增加。
4. 当前 WA 新增的 CP-drop 更新标志仍未完成端到端数据包行为核实。不能把 CP 字样直接解释成 TCP ACK 保护，更不能默认开启未经 ABI/资源映射验证的原厂完整配置。

优先排查方向仍为：同一 TID/AC 的上行数据与 ACK 的排队、空口机会、AP 触发/接收调度互操作。手机此前复现，所以不将其归咎于电脑 NFA765。没有终端队列可见性或同步空口采集时，尚不能区分具体责任落在终端内部队列、AP 策略还是二者交互。

## 四、Wi-Fi 消失：首条命令与恢复链重新核对

### 命令含义

按当前 mt76 命令编码：

```
0x00130022 = WM(bit20) | UNI(bit17) | QUERY(bit16) | ID(0x22)
ID 0x22 = MCU_UNI_CMD_GET_MIB_INFO
```

实际发送位置为 `mt7996/mcu.c:5453` 的 `MCU_WM_UNI_CMD_QUERY(GET_MIB_INFO)`。它是信道/MIB 计数查询，**不是温度 ADC 查询，也不是 BA 或 VOW 量子写入命令**。这是依照当前源码对旧日志命令号的解释，未声称已对旧固件每个函数做二进制符号验证。

### 两次旧故障的顺序

以下时间全部使用同份日志中的内核 uptime，相对于首条记录的 MIB 超时：

| 记录 | 首条 AER 报告 | 输出 CmpltTO 位 | 固件初始化超时 |
| --- | --- | --- | --- |
| 11月7日 21:33 | +0.311s | +0.556s | +2.540s |
| 11月10日 16:47 | +0.094s | +0.522s | +2.550s |

两次都随后记录 `no error_detected callback`、`device recovery failed`，11月10日又多次记录 `Firmware is not ready for download` 和 `chip full reset failed`。原文路径、输入 SHA256、关键行、时间差见 `other-path-fault-correlation.json`。

**打印顺序不是底层故障发生顺序。** MCU 响应缺失、PCIe 报错触发、AER 中断和日志输出存在不同延迟；MIB 超时也可能只是周期性查询先观察到芯片已无响应。

### 代码中确认的恢复限制

- 当前 `mt7996_mcu_parse_response()` 在普通命令无响应时安排 `reset_work`，走全芯片复位。
- 当前 WDT 异常路径才先安排 `dump_work`，收集固件转储后再复位。普通查询超时不经过同一转储流程，所以现有日志不能定位到复位前的 WM/WA PC、栈或最后一个锁等待。
- `mt7996_mac_full_reset()` 停 NPU/队列后重建 DMA 并重载固件，失败最多重试 10 次。它不是 PCIe 根端口重训练/掉电复位。
- 当前 `pci.c` 仍未注册 `pci_error_handlers`，与旧日志里的“没有 error_detected 回调”相符。这是 AER 框架无法协同恢复的明确缺口，但不是最初故障的证据，也不意味着填一个返回 CAN_RECOVER 的空回调就能修好。

因此有三条尚未区分的链：

1. 固件/芯片先停止响应 → MIB 超时 → 复位期间进一步出现 PCIe 错误。
2. PCIe 访问先异常 → 命令响应缺失 → MIB 超时 → 后续 AER 输出。
3. 双方共有的 DMA/总线/电源状态先异常 → MCU 与 PCIe 都失效。

现有证据不能直接认定为 PCIe3.0×2 信号问题，不能通过屏蔽 AER、延长等待或不复位就声称根治。

## 五、与已测现象对照后的取舍

| 候选 | 当前证据 | 判断 |
| --- | --- | --- |
| WA 优先级/AC 映射版本差异 | 完整函数16384组一致 | 此处未找到差异，排查优先级降低 |
| BA 窗口16位被错误截成8位 | 主机发le16、WA读lhu；实际缩窗也未解决 | 未支持该假设，完整状态机仍需核对 |
| 默认 RED 缺失 | 主机初始化发送关闭；原厂策略不同 | 可研究的差异，尚非经验证根因 |
| AP 下行软件队列单独造成全部低速 | 已有ACK分段的大头在AP接收前 | 与现有主要延迟位置不符 |
| 电脑网卡驱动单独故障 | 手机也复现 | 不作单一原因 |
| NPU 必然是2.4GHz根因 | 本机端点、关闭NPU的前轮仍可复现 | 非必要触发条件；转发路径会改变分配 |
| MIB查询超时后全芯片恢复失败 | 日志与当前恢复代码对应 | 能解释三频一起消失及无法自动恢复，尚不能解释首次卡死的根源 |

下一步最有区分力的证据是：普通 MIB 超时后的复位前有界快照（优先保存主机已有状态，避免失联时大量读 MMIO）；若总线仍响应，再保存 WM/WA PC/栈/异常状态。2.4GHz 则需要空口中的逐 TID 发送、重试、BA 与 Trigger 时间线。没有这些证据，不把增加调度移植的数量当作根因已经确定。

本轮只提交独立逆向/复算工具和报告，保持现有固件行为。未作虚假的“已修复”结论。
